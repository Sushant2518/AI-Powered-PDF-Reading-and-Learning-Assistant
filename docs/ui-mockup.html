Idempotence

An operation is idempotent if performing it several times has the same effect as performing it once. Setting a key to a fixed value is idempotent; incrementing a counter is not.

Idempotence matters because networks are unreliable. When a client sends a request and the response times out, the client cannot know whether the server processed it. Retrying is only safe if the operation is idempotent — otherwise a payment might be charged twice.

A common technique is to attach a unique request ID to every operation. The server records the IDs it has already processed and ignores duplicates. Combined with retries, this gives effectively-once processing, even though messages may be delivered more than once.

📄 From your PDF · p.472

If you do the same thing twice and the result is the same as doing it once, the action is idempotent. Setting x = 5 is idempotent. Doing x = x + 1 is not.

Why care? Networks fail. If your request times out, you don't know whether the server did the work. Sending it again (a retry) is only safe for idempotent actions. Otherwise a customer could be charged twice.

The usual fix: give every request a unique ID. The server remembers which IDs it already handled and skips repeats. So even if a message arrives twice, it is processed only once ("effectively-once").

Idempotence Distributed

Definition
Doing the same request twice has the same effect as doing it once.
Why it matters
Clients must retry after timeouts. Without idempotence, retries create duplicates (double payments, double emails).

Trade-offs
• Storing keys costs space → expire them (e.g., 24 h)
• Must store the response, not just the key

        
Common mistakes
• Assuming POST is idempotent
• Checking the key without a UNIQUE constraint (race condition)

What's current

        
• The IETF HTTP APIs working group has a draft that standardises an Idempotency-Key request header for non-idempotent methods like POST. [1]

        
Background

        
• HTTP defines PUT, DELETE and the safe methods (GET, HEAD, OPTIONS, TRACE) as idempotent. [2]

        
In the real world

        
• Stripe's API accepts an idempotency key on POST requests so clients can retry safely. [3]
